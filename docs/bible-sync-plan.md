## 목표 형식

```
sentence = (해당 절이 구역 시작이면) "<구역제목> " + 원본 본문
```

- 구역 제목은 원본 응답의 `theme` 필드(`[{start_jul, cont}]`)에서 복원한다. 기존 DB의 `<천지 창조> 태초에…` 형식과 동일한 관례다
- 원본의 `○`는 **그대로 보존**한다. 본문을 훼손하지 않기 위해서이며, **표시할 때 제거하는 것은 프론트 담당**(QT·말씀카드)

## 반영 방법

- **마이그레이션 파일**로 반영한다 (원격 직접 쓰기 금지 규칙 준수 — CI가 staging→prod 순서로 적용)
- `supabase/seed.sql`도 교정 후 데이터로 재생성한다. 이후 로컬/스테이징 리셋 시 **seed 자체가 진실 원천 사본**이 되어 이번 같은 되돌림이 재발하지 않는다

### 마이그레이션과 seed 의 공존 — INSERT 는 빈 테이블에서 건너뛴다

`db reset`은 **마이그레이션을 먼저 적용하고 그다음 seed를 적재**한다.
누락 절 INSERT를 무조건 실행하면 빈 테이블에 14행이 먼저 들어가고,
뒤이어 같은 id를 담은 seed가 들어오면서 `bible_id_key` 중복으로 리셋 전체가 실패한다
(실제로 처음 구성에서 이 실패를 겪었다).

```sql
insert into "public"."bible" (...)
select v.* from (values ...) as v(...)
where exists (select 1 from "public"."bible")   -- 빈 테이블이면 아무것도 넣지 않는다
on conflict ("id") do nothing;
```

- **로컬/CI(빈 테이블)**: INSERT가 통째로 건너뛰어지고 seed가 전량을 적재한다 (seed는 이미 교정본)
- **원격(데이터 있음)**: 정상 실행되어 누락 절이 추가된다
- UPDATE·DELETE는 빈 테이블에서 자연히 무해한 no-op이라 별도 가드가 필요 없다

## 검증 결과 (2026-07-28)

교정 적용 → seed 재생성 → `supabase db reset` 재생 → **재생된 DB를 원본과 다시 전수 대조**했다.

| 항목 | 결과 |
|---|---|
| 재생(`db reset`) | 성공 — 마이그레이션 + seed 무오류 |
| 원본 대조 | **1,189장 / 31,102절 전수, 불일치 0건, API 오류 0건** |
| 행 수 | 31,138 → **31,102** (추가 14, 삭제 50) |
| `paragraph = 0` | **0행** |
| 깨진 문자(`long_label`/`sentence`) | **0행** |
| 책 수 | 66 |

seed 왕복(SQL 이스케이프)에서의 훼손 여부까지 확인하기 위해, 대조는 파일이 아니라
**재생된 로컬 DB에서 직접 읽어** 수행했다.

## 배포 순서 — 이번 건만 **web 먼저 → Api**

평소 규칙은 `Api 먼저 → web`이다. web이 새 스키마·함수에 의존하기 때문인데, **이번 짝은 그 의존이 없다.**
반대로 Api가 먼저 나가면 본문에 들어온 `○`가 **구버전 web에서 그대로 노출**된다.
web을 먼저 내보내면 아직 없는 표기를 지우는 no-op이라 무해하다.
